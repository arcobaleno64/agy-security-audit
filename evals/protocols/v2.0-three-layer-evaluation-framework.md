## 1. Executive Summary & Governance Purpose

This document establishes the **V2.0 Three-Layer Evaluation Framework**, serving as the authoritative umbrella governance protocol for evaluating the precision, recall, uncertainty calibration, and fail-closed integrity of `@arcobaleno64/agy-security-audit`.

The core research question governing this framework is:
> **Can the security audit system reliably discover authentic security vulnerabilities, accurately signal epistemic uncertainty (`UNVERIFIED`), and suppress false positives on clean code across diverse projects and vulnerability domains—without hallucinatory confidence?**

### 1.1 Non-Equivalence Principle (Sample Sufficiency != Evaluation Success)
A foundational tenet of this framework is:
```text
Sample sufficiency != evaluation success
```
Collecting or executing the target number of benchmark cases satisfies only the *observational breadth prerequisite*. Evaluation success requires passing all 8 dimensions of the master scorecard and incurring **zero violations** of the non-negotiable hard stops.

### 1.2 Relationship to Legacy Protocols
This framework does **not** discard prior empirical efforts, nor does it grant them automatic compliance:
- Historical protocols (`v1.5-cross-model-protocol.json`, `v1.5-eval-1.json`, `v1.5-g5-ablation-execution-1.json`, `v1.6-g8r-cross-provider-protocol.json`, `v1.6-oss-transfer.json`) remain preserved in the repository as immutable historical evidence.
- Existing evidence matrix artifacts (e.g., target version `1.9.2` with dimensions `SUPPORTED` and overall status `SUBSTANTIATED`) remain valid for their historically documented scopes.
- **Legacy Evidence Re-Certification Invariant**: Historical evidence **MUST NOT** be automatically grandfathered as satisfying V2. Existing fixtures and runs may only be incorporated into Layer 2 after undergoing formal re-certification against V2 Ground Truth Bundle, paired-control, and taxonomic diversity criteria.

## 2. Three-Layer Architecture

To prevent conflating deterministic software contracts with empirical model behavior, evaluation is structured into three strictly partitioned layers:

```
+-------------------------------------------------------------------------+
| Layer 1: Deterministic Integrity & Regression                           |
| - Automated Contract & Invariant Tests (Default-Deny, SARIF, AST, CLI)  |
| - Zero LLM dependency; hermetic; 100% pass required                     |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
| Layer 2: External Validity Corpus (12-16 Paired / Controlled Cases)     |
| - 6-8 Known Vulnerable Cases                                            |
| - 3-4 Fixed / Patched Counterparts                                      |
| - 3-4 Clean Negative Controls                                           |
| - Ground Truth Bundle binding upstream commits and technical evidence   |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
| Layer 3: Fresh Shadow Cohort (10-15 Fresh External Changes)             |
| - In-the-wild changes from external repositories                        |
| - Primary evaluation of real-world generalization                       |
| - Pre-run Human Security Oracle adjudication                            |
+-------------------------------------------------------------------------+
```

### 2.1 Layer 1 — Deterministic Integrity & Regression
Layer 1 evaluates the software platform, runtime guards, and schema contracts underlying the audit agent.
- **Scope**: Hermetic, offline automated tests executed via `npm test` and `node --test`.
- **Contracts Enforced**:
  1. *Default-Deny & UNVERIFIED Enforcement*: Verifier ballots default to unverified unless positive proof is established.
  2. *Patch Jail Confinement*: Fix verification guarantees that remediations never touch unauthorized files or CI workflows.
  3. *SARIF 2.1.0 Fidelity*: Deterministic rendering, stable fingerprint generation, and standards mapping (NIST SSDF SP 800-218, OWASP ASVS v5.0.0).
  4. *Shadow Context Confinement*: Strict path containment, preventing leakage of uncontained repository data.
- **Pass Gate**: 100% test pass rate across supported Node and OS matrices. Zero regressions tolerated.

### 2.2 Layer 2 — External Validity Corpus
Layer 2 evaluates vulnerability detection capability using an authoritative, curated corpus of **12 to 16 high-quality, adjudicable cases**.
- **Case Distribution**:
  - **6–8 Known Vulnerable Cases**: Real-world security vulnerabilities with confirmed security impact.
  - **3–4 Fixed / Patched Counterparts**: The corresponding remediations for the vulnerable cases.
  - **3–4 Clean Negative Controls**: Non-vulnerable, functionally complex codebases or refactorings that stress the audit system without containing flaws.
- **Taxonomic Diversity**:
  Cases must span at least seven distinct vulnerability families:
  1. *Injection & Validation* (CWE-89, CWE-79, CWE-78)
  2. *Authentication & Authorization* (CWE-287, CWE-863, CWE-639)
  3. *Path & Filesystem Boundaries* (CWE-22, CWE-59)
  4. *Deserialization & Parser Boundaries* (CWE-502, CWE-125, CWE-787)
  5. *Concurrency & State Lifecycle* (CWE-362, CWE-662)
  6. *Secrets & Configuration* (CWE-798, CWE-200)
  7. *Dependency & Supply-Chain Integrity* (CWE-1395, CWE-1104)
- **Paired Vulnerable/Fixed Design**:
  To measure both recall and precision, vulnerable cases should be paired with their official fix commits whenever possible. A security tool that flags both the vulnerable and the fixed version for the same vulnerability fails precision.

### 2.3 Layer 3 — Fresh Shadow Cohort
Layer 3 evaluates the system against fresh, contemporary external pull requests and commits before or concurrent with upstream human review.
- **Sample Requirement**: **10–15 fresh external changes**.
- **Execution Mode**: Advisory shadow execution (shadow review).
- **Oracle Determination**: Evaluated against pre-run Human Security Oracle review, as upstream public CVEs or official security advisories may not exist at the time of observation.

## 3. Future Blocking-Authority Promotion Gate

The requirements under V2 distinguish between an **Advisory Security Reviewer** and an **Autonomous Blocking Authority**:

| Authority Level | Operational Scope | Empirical Requirement | Promotion Gate |
| :--- | :--- | :--- | :--- |
| **Advisory Baseline** (Current) | Generates security findings, alerts, and SARIF reports for human review. | Layer 2: 12–16 cases<br>Layer 3: 10–15 fresh cases | Pass 8-dimension scorecard; 0 Hard Stop violations. |
| **Blocking Authority** (Future) | Enforces mandatory CI merge/release blocks; certifies code as "Security Clean". | Layer 2: 16+ cases<br>Layer 3: **20–30+ fresh cases** | False Advance = 0 across cohort; strict dual-lens verification; re-certification audit. |

> [!CRITICAL]
> The asymmetric penalty of a **Security False Advance** (declaring code "Security Clean" when exploitable vulnerabilities persist) is significantly higher than general code review false approvals. Therefore, granting blocking or clean-certification authority requires escalating the cohort to at least 20–30 fresh cases and enforcing an uncompromising promotion gate.

## 4. Ground Truth Bundle Protocol

No candidate case qualifies for Layer 2 or Layer 3 without an authoritative **Ground Truth Bundle**.

### 4.1 Layer 2 Ground Truth Bundle Requirements
For Layer 2 corpus fixtures, the Ground Truth Bundle must consist of:
1. **Upstream Commit Identity**: Exact Git repository URL and immutable Commit SHA (or tagged release).
2. **Authoritative CVE / Security Advisory**: Public CVE ID or upstream security advisory affirming the vulnerability.
3. **Reproducible Technical Evidence**: A concrete Proof-of-Concept (PoC), failing test case, or deterministic exploit script demonstrating reachability and exploitability.
4. **Human Security Oracle Mapping**: Expert human security review documenting:
   - Target vulnerable sink and input source (with line locators).
   - Expected CWE and severity rating.
   - Exact criteria distinguishing the vulnerable state from the patched state.

### 4.2 Layer 3 Ground Truth Bundle Requirements
For Layer 3 fresh shadow cases:
1. Exact commit SHA and repository URL.
2. Pre-run Human Security Oracle analysis frozen *prior* to unblinding or analyzing tool output.
3. Post-run reconciliation record comparing upstream reviewer feedback, author resolution, and independent verification.

### 4.3 Separation of Triad-Flow
`triad-flow` may serve as an observational orchestration framework or execution harness for `agy-security-audit`. However:
> **Triad-Flow outputs MUST NEVER serve as ground truth for agy-security-audit.**  
Ground truth must originate strictly from external ground truth bundles, confirmed CVEs, reproducible exploits, and independent human security oracles. Circular AI-proving-AI validation is explicitly prohibited.

## 5. Master 8-Dimension Scorecard

Every evaluation cohort must report metrics across all eight dimensions:

| Dimension | Metric | Definition & Evaluation Objective |
| :--- | :--- | :--- |
| **D1: Must-Detect Recall** | $\text{Recall}_{\text{critical}}$ | Percentage of designated must-detect vulnerabilities correctly identified with accurate root causes and sinks. |
| **D2: False-Positive Rate (FPR)** | $\text{FPR} = \frac{\text{FP}}{\text{FP} + \text{TN}}$ | Percentage of clean controls or non-vulnerable lines incorrectly flagged as blocking security flaws. |
| **D3: Severity Agreement** | $\kappa_{\text{severity}}$ | Concordance between predicted severity (CVSS v4.0) and ground-truth oracle severity. Downgrading criticals is heavily penalized. |
| **D4: UNVERIFIED Correctness** | $\text{Acc}_{\text{uncertain}}$ | **Epistemic Calibration**: System correctly issues `UNVERIFIED` when evidence/context is incomplete, rather than hallucinating `CLEAN`. |
| **D5: Fail-Closed Correctness** | $\text{Rate}_{\text{fail-closed}}$ | System successfully defaults to denial or human review upon timeouts, schema errors, or missing call-graph context. |
| **D6: Finding Provenance** | $\text{Precision}_{\text{loc}}$ | Accuracy of vulnerability source-to-sink locators (file paths, line numbers, and data-flow traces). |
| **D7: SARIF Fidelity** | $\text{Pass}_{\text{sarif}}$ | Schema validity against SARIF 2.1.0, stable rule IDs, and valid NIST SSDF / OWASP ASVS mappings. |
| **D8: Cross-Project Generalization** | $\sigma_{\text{recall}}$ | Consistency of recall and precision across different programming languages, frameworks, and repository scales. |

## 6. Non-Negotiable Hard Stops

Any single occurrence of the following five conditions triggers an immediate **COHORT REJECTION (FAIL)** regardless of sample size or aggregated percentage scores:

1. **False CLEAN on Designated Must-Detect Vulnerability**  
   If the audit system certifies a known, reachable, must-detect vulnerability as `CLEAN`, the run FAILED.
2. **Incomplete or Unverifiable Evidence Reported as CLEAN**  
   If context gaps, truncated callees, or unresolved macros exist, certifying `CLEAN` instead of `UNVERIFIED` is a critical failure.
3. **Synthetic Evidence Represented as Live Observation**  
   Submitting mock, replayed, or synthesized LLM runs under the guise of live execution disqualifies the evaluation.
4. **Security False Advance in Fresh Shadow Cohort**  
   If a fresh shadow PR with an exploitable vulnerability is certified `CLEAN` or approved without findings, the cohort is immediately **HALTED** for Root Cause Analysis (RCA).
5. **Unbound Ground-Truth Provenance**  
   Any case lacking independently verifiable upstream commit binding or technical proof cannot qualify for evaluation metrics.
